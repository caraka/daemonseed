# Design: Veilid write budget — presence model, write scheduler, record layout

Status: **FROZEN + RATIFIED 2026-07-09** (initial cadence [180,220]s / TTL 600s ratified with the structure). Hardened by a 3-lens adversarial panel (metadata/traffic-analysis, ordering/consistency, quantitative/mechanics) plus an independent advisor pass; findings integrated below. Tracking issue: #159 (write saturation, Tier-2 structural). Couples: #157 (share-advert discovery layout), #77 (circle presence, gated on this design), #141 (write amplification), #154 (actor inline-park — subsumed by the scheduler), #158 (operator-record expiry — served by the deadline rule). Lineage: `docs/design/phase4-veilid-presence-announcements.md` (decisions P1/P2 stand), `docs/design/veilid-migration.md`.

## Problem

Veilid `set_dht_value` is a seconds-per-write discovery primitive; daemonseed imposed a high volume of open-loop periodic writes on it. Measured (2026-07-09, live public Veilid, 3 circles + shares + lobby): writes backed up to 90–314s, starving chat delivery, presence freshness, and share-advert route refresh (#159 — one root cause, three faces). The per-member presence beacon was the dominant writer at its cheapest config (lobby-only); #77 circle presence multiplies presence writes by (1 + N circles), so no cadence value survives scaling. Tier-1 (beacon cadence [15,20]s → [50,55]s, the #159 commit) relieved the acute saturation — write latency dropped to 1.4–5.8s — but is a parameter fix on an unpriced commons: every writer (presence timer, advert refresh, MOTD keepalive, warmup resweep, chat publish) draws on shared DHT write capacity with no allocation mechanism, and the presence reaper's TTL is calibrated to emit cadence while its input (beacon arrival) is latency-dependent — under congestion, false reaps are the *expected* behavior, not an edge case.

A coupled defect in the same design space: #157 — share adverts are placed at `current_state_subkey(share_id)`, a slot addressed by the share's own id. A reader can only read a subkey it can compute, and it cannot compute the slot for a share whose id it learns *from* the advert. Cross-client share discovery deadlocks.

## Constraints (must hold)

- **ISC-A-S2** — the network sees only sealed frames; no enumeration of circles, membership, or participant identity; traffic shape must not reveal activity patterns. Correlation attacks are in scope (Level-C adversary).
- **Roster-as-presence** (ISA `## Principles`, Demonsaw lineage) — on the roster = online; appear/disappear; no read-receipts/typing/dots. A connected-but-silent member MUST appear. The product shape is fixed; only the mechanism is in play here.
- **~14.7s cross-node DHT watch propagation floor** (measured) — presence resolution is tens-of-seconds by physics.
- **Per-record guarantees stand:** `record_lock` single-flight per record; ring seq assignment inside the lock; clamp-at-insert `order_ms` (#131). Nothing in this design may re-open them.
- **P1/P2 stand** (phase-4 design-of-record): presence rides its own sibling record with last-writer-wins member slots; cadence sits above the watch floor.

## The reframe

Presence is fundamentally a *read* question — "who is here right now" — that was built as a high-frequency *write* (every member re-writes its own liveness every interval). Decomposed, presence is: (a) a liveness **claim** by a member (costs a write), (b) a liveness **judgment** by each receiver (free local computation), (c) a transport carrying (a) to (b) (the watch every client already holds). Only the claim costs writes, and for active members the receiver already holds fresher evidence than any beacon: their chat messages. The design moves everything movable to the read side.

The tempting cheap answer — derive liveness *entirely* from message activity — fails both fixed constraints: it makes a lurker invisible (roster-as-presence violated) and, applied to emission timing, turns presence traffic into an activity oracle (ISC-A-S2 violated). The panel + advisor pass sharpened where the line actually is. It is **not** write-vs-read — a read-fetch (GET) is a network-observable event exactly like a write. The line is:

## WB-0 — FROZEN: the invariant (the spine of the design)

> **User activity may influence only local computation. It must never influence the timing, size, or existence of any presence/discovery-class network emission — write or read-fetch.**

Scope notes, each load-bearing:

- **"presence/discovery-class"** — chat writes are inherently activity-coupled: the activity IS the payload, and sending it is the user's explicit, consented emission. The invariant governs everything *around* chat: presence, adverts, keepalives, and any read-fetch. What presence hardening buys, precisely: it protects the **residual activity chat does not already reveal** — lurking, reading, session rhythm, share churn.
- **"timing, size, or existence"** — size is included because AEAD is length-preserving: a variable-length sealed payload is a plaintext-metadata oracle to any key-free observer (panel finding: the current beacon's `sender_handle` + `live_share_ids` fields make ciphertext length a share-count-and-change-time channel).
- **"or read-fetch"** — freshness inputs must arrive only via the constant-cadence watch/sweep channel already running; an on-demand GET triggered by opening a room or checking a roster is an activity-timed emission.
- **Derived rule (the future-proofing clause):** *no read/render event may enqueue a non-cadence emission.* Read receipts, delivery acks, "last-active" bumps, unread-counter writes — every one is an activity-coupled write wearing a read costume, and each is forbidden by contract, not just absent from the current product.
- **Trust boundary (named):** presence privacy holds against out-of-room, network, and DHT-storage observers. It never holds against in-room peers — the roster shows members each other's presence *by design*; that is the product, not a leak.

## WB-1 — FROZEN: presence model = constant-cadence fixed-length keepalive + read-side inference

A hybrid of periodic-keepalive and activity-derived liveness, with the activity coupling confined entirely to local computation (WB-0).

**Write side (activity-independent, per joined room's presence sibling record):**

1. **Join write** — one presence beacon published on subscribing to a room (session boundary; presence *is* session liveness, so this reveals nothing beyond what the roster displays).
2. **Keepalive** — a sealed presence beacon every **[180,220]s jittered** (initial value; tunable band [120,300]s under the WB-2 ceiling). The cadence takes no input from user activity — not sends, not reads, not self-inflicted congestion. Jitter is drawn fresh per emission (no fixed phase relationships — see WB-3.I6 note on cross-record linkage).
3. **Leave write** — a tombstone beacon on graceful close, inside the existing close budget (the #121 pattern). Explicit close is business-as-usual; the TTL is the crash backstop only — the same lifecycle doctrine already ratified for shares.
4. **Fixed length (panel BREAK, adopted).** All presence-class writes — join, keepalive, leave tombstone — seal to **one constant byte length**, padded before sealing. Without this, ciphertext length tracks the variable payload (`sender_handle`, `live_share_ids`) and a key-free storage node reads share counts and timestamps every share add/remove; a shorter tombstone would hand it a clean session-end marker. The padding constant and overflow policy are the build's choice; the builder SHOULD evaluate moving `live_share_ids` out of the beacon entirely — post-#153 the share record is its natural home.

**Read side (all the intelligence lives here — and it is emission-free by contract):**

5. **Freshness** — `freshness(member) = max(last presence beacon, last verified same-room member write)`, **dominated by the leave tombstone**: once a leave with timestamp `leave_ms` is applied, no same-room write with `sent_unix_ms ≤ leave_ms` may re-freshen the member (panel BREAK: without dominance, a final chat message racing the tombstone across sibling records flickers a departed member back onto the roster). A genuinely *newer* write (a rejoin, a post-leave message) re-freshens normally.
6. **Same-room bound** — freshness input is restricted to the same room's sibling records. Cross-room derivation is forbidden (anti-criterion): if lobby presence consumed circle activity, a public surface would timestamp private-circle actions.
7. **Watch-delivered only** — freshness inputs arrive via the constant-cadence watch/sweep channel already held; no freshness path may issue an on-demand GET (WB-0).
8. **Emission-free contract** — no freshness inference or reap transition may schedule any network emission (write or fetch). The read side is where activity coupling is safe *because* it emits nothing; this clause is what keeps that true as the product grows.
9. **Reap** — a member leaves the roster when `now − freshness > TTL`, **TTL = 600s** (= 2 × keepalive-max 220s + 160s slack for queue + write + propagation; deliberately the same constant class as the share TTL backstop — one liveness doctrine).
10. **Reap only in calm** — reaping is suspended while the local congestion signal is elevated. The signal is **enqueue-to-ack latency** (queue wait + record-lock wait + set RTT), not set-RTT alone (panel BREAK: a calm DHT with a deep local queue would otherwise false-reap members whose keepalives sit in the funnel). Suspension only ever *delays* disappearance — bias-to-forgiveness.
11. **Collision handling (panel-corrected — absorption is partial).** Presence slots are `current_state_subkey(hex(member pubkey))`: hash-mod placement with birthday collisions (~37% pair-collision at 8 members over 64 slots; ~85% at 16 — at lobby scale collisions are the norm, not the exception). Under last-writer-wins, TTL = 2 × keepalive-max + slack absorbs the *antiphase* case (writes ~half a cadence apart: each member surfaces every ~2 keepalives, 3× margin inside 600s). It does NOT absorb *phase-lock*: if B habitually overwrites A's slot within the ~14.7s watch-settle window, the watch reports only B, and a **silent** colliding member — the exact member roster-as-presence exists to protect — can false-reap despite beaconing on time (an active member is rescued by the read-side fold; a lurker is not). Two clients that joined together draw phase-adjacent jitter for many cycles, so phase-lock is not exotic. Consequence: the **#77 build MUST resolve presence slot collisions** (dedicated larger presence schema and/or disjoint per-member regions); the alpha tolerates the residual at lobby scale with ephemeral identities. (For contrast: the *built* lobby reaper today runs TTL 60s against a 52.5s beacon — under 1.15 intervals of tolerance, which is the #159 flicker; this design's 600s + read-side fold is the fix.)

**Why this holds ISC-A-S2 (hard-to-vary, clause by clause):**

- *Constant cadence + fixed length* (2, 4): the presence record's write pattern is a jittered constant rate of constant-size sealed values, independent of everything the user does. Nothing in timing or size correlates with message activity, room activity, or share churn, because no such input reaches the emission path.
- *Session-boundary writes* (1, 3): join/leave writes reveal session liveness — which IS the product; no presence mechanism can hide what presence displays. The tombstone is byte-identical to a keepalive (4), so a key-free observer cannot even distinguish leave from keepalive; only cessation is visible, as it must be.
- *Read-side inference* (5–8): local computation over ciphertext already delivered on a constant-cadence channel. The network cannot distinguish a client that infers freshness from one that doesn't — there is no emission to observe, and clauses 7–8 make that a contract rather than a current accident.
- *Reap-in-calm* (10): consumes the receiver's own locally-observed latency — never any member's activity — and produces no emission.
- Every clause is load-bearing: drop 2 or 4 and presence traffic becomes an activity/share oracle; drop 5's dominance and departed members flicker back; drop 6 and public surfaces timestamp private activity; drop 7 or 8 and read-timing becomes the new leak; drop 10 or 11 and flicker returns under congestion or collision; drop 1/3 and either lurkers vanish (product violation) or ghosts become the norm rather than the crash case.

**Named residuals (accepted, panel-reviewed — honesty over marketing):**

- **Storage-node slot-occupancy channel.** A DHT node hosting a presence record observes, key-free: populated-slot count (≈ member cardinality) and per-slot write cessation (session end ± TTL). On stable-identity records (#77 circles) a logging co-host accretes a per-pseudonym session time-series (sleep/wake rhythm). Mitigations: circle record addresses are secret-gated (an adversary cannot *target* a chosen circle, only opportunistically co-host), identities are pseudonymous, lobby identity is ephemeral (no cross-session linkage), and this design's lower cadence shrinks the channel vs. the baseline. Shared by every candidate presence model; eliminated only by cover traffic, which is out of scope here.
- **Session-boundary burst linkage.** Connect writes join beacons to all joined rooms inside the connect window; close writes tombstones in the close budget. An observer co-hosting two of a client's records can link pseudonyms by coincident bursts. Private routing strips the source, so linkage is timing-coincidence only. The builder MAY disperse join writes across the connect window; leave bursts are inherent to closing.
- **Dispatch-timing independence.** A keepalive enqueued on time can dispatch late when the client's own queue is busy — a correlated bias that zero-mean jitter does NOT conceal (statistical distinguishability is about correlation, not magnitude). WB-3.I6 therefore demands statistical *independence* of keepalive dispatch timing from other-class load, and the WB-ISC-1 probe tests distribution-indistinguishability, not "within the jitter band."
- **Protocol detection is out of scope.** Constant-cadence presence resists activity correlation but is itself a regular-heartbeat signature (plus the app-wide `DHTSchema::dflt(64)` fingerprint) to a censor asking "is this daemonseed?" — a *detection* question, deferred to Veilid transport-level obfuscation. This design is strictly better than the baseline on detectability (fewer, wider-spaced writes) but does not claim to solve it.

**Trade (explicit, for ratification):** crash/network-loss ghosts persist up to TTL ≈ 10 min (vs ~45s today — but today's 45s is also the flicker). Graceful close disappears immediately via the leave write. Faster ghost-reaping is purchasable by narrowing the keepalive band within its tunable range at write-budget cost — the dial is cadence; the invariant is the WB-2 ceiling.

## WB-2 — FROZEN: write-budget ceiling + oracle

**Load model:** lobby + 3 circles (#77 on) + 2 live shares + operator MOTD.

**Ceiling:** steady-state **≤ 4 non-chat DHT writes/min per client** (≤ 4.5 for an operator, MOTD keepalive included). **Connect window:** the first 120s after connect may additionally spend up to 8 one-shot writes (join beacons, share-advert republish). Chat is user-action-rate and excluded from the ceiling; WB-3 guarantees it never queues behind budgeted traffic.

**Arithmetic (panel-corrected — these are WB-1 target numbers, not the current code's):** presence at the WB-1 band = 4 rooms × 60/200s ≈ 1.2/min (presence scales **linearly in room count** in every model — (1+N) records × cadence; what the freeze changes is the *per-room rate*, ~11× lower than the built [50,55]s band. The built band at 4 rooms would be ≈ 4.6/min — already over this ceiling, which is why the ceiling is met only once the WB-1 cadence lands). Share adverts: **quiescent** = watchdog-paced ≤ 0.8/min for 2 shares; the reactive path (`RouteMaintenance` refresh, coalesced to a 5s floor) has a churn worst case of `adverts × 12/min` — under sustained route churn that is ~24/min for 2 shares, and it is the WB-3 funnel (I5 cap + I3 coalescing), **not cadence**, that bounds it. MOTD keepalive = 0.5/min (operator only). Steady totals ≈ 2.0–2.5/min — half the ceiling. Empirical anchors: ~6+/min saturated the DHT (90–314s writes); ~2/min ran healthy (1.4–5.8s writes, the #159 Tier-1 re-test); the ceiling sits with measured-healthy as the design point and ~2× headroom below measured saturation.

**Connect window basis:** subscribes/rejoins/resweeps are reads, not writes; connect-time writes = one join beacon per room (a WB-1 addition — no join beacon exists in current code) + one republish per persisted share. The 8-write allowance covers the load model (4 + 2 = 6) with margin; the general bound is **≤ rooms + persisted shares**, and a user restoring many shares scales past 8 by that formula, not by exception.

**Read budget (panel gap, adopted):** `sweep`/`resweep` are 64 force-refreshed GETs per record and bypass any write funnel; ungoverned, a warmup read-burst co-occurs with the connect-window writes against the same DHT nodes. Reads are paced in their own lane (the #140 warmup taper plus WB-4's steady-state discovery resweep are its governors) and the oracle counts read ops against a declared read ceiling alongside writes.

**Oracle (named, for the build — panel-corrected):**
1. **Paused-time scheduler test.** The current actor has no mock seam over `set_dht_value` (the write path calls `RoutingContext` directly; only the fetch path is closure-injected). The buildable oracle is therefore a paused-time unit test over the **WB-3 scheduler component**, with an injected write-sink counter and clock: drive the load model ≥ 30 simulated minutes; assert steady-state dispatch ≤ ceilings and connect-window ≤ allowance. The WB-3 build MUST introduce that seam (the funnel is the natural place); the oracle is stated against it, not against the unseamed actor.
2. **Live-trace counter** (orinoco felt-test, not CI) — `DAEMONSEED_VEILID_TRACE=1` log: `write ok` lines per 60s window ≤ ceiling; secondary assert: p95 write latency single-digit seconds.

## WB-3 — FROZEN: write-scheduler invariants

The scheduler build is night-runnable mechanics; these invariants are its contract.

- **I1 — single funnel.** Every `set_dht_value` in the actor passes through one prioritized, rate-limited queue. Priority classes, highest first: (1) chat/user-action, (2) session-boundary presence (join/leave) and share withdraw, (3) share-advert refresh, (4) keepalives (presence, MOTD), (5) post-warmup republish writes. No writer bypasses the funnel. (Resweep *reads* are not class-5 members — they ride the WB-2 read lane; class 5 is the write half only.)
- **I2 — per-record FIFO; slot/seq assignment at dispatch.** Priority reordering applies **across records only**. Writes to the same record dispatch in enqueue order, and ring seq / slot selection happens inside the record's `record_lock` at dispatch time — never at enqueue. This preserves append-ring atomicity and #131 untouched. Cross-record reordering is safe for *ordering* because those guarantees are per-record; the one cross-record *semantic* fold — presence freshness — is protected by WB-1.5's leave-dominance, not by dispatch order.
- **I3 — coalescing.** Last-writer-wins current-state writes (keepalive, advert, MOTD) coalesce in-queue: a queued write superseded by a newer write **for the same (record, logical id)** is dropped. The coalescing key is the logical id (member id, share id, "motd") — never the physical subkey (hash collisions would starve a colliding member entirely, voiding WB-1.11's absorption math). **Tombstones and withdraws are non-coalescible and dominate**: a queued withdraw/leave is never superseded by any same-id current-state write regardless of enqueue order (panel BREAK: a watchdog advert-refresh queued after a withdraw would otherwise resurrect a withdrawn share — the #121/#118 regression class). Chat ring writes are never coalesced or dropped.
- **I4 — chat latency bound (scoped).** A chat write to a **record with no earlier same-record write in flight** begins its DHT dispatch ≤ 2s after enqueue regardless of queue depth; chat is never counted against I5's non-chat cap and always holds a reserved dispatch slot. For back-to-back chat on one record, the per-record `record_lock` (held across the DHT set — a constraint this design does not re-open) makes per-record chat throughput = one set-RTT per message; the bound is therefore per-record-idle, and the felt-test failure mode this invariant kills is chat waiting behind *budgeted* traffic, which remains forbidden unconditionally.
- **I5 — bounded in-flight.** Non-chat in-flight DHT sets are capped (initial cap 2); the queue rate-limits, not merely orders. The dormant signal-agnostic `AimdWindow` (`crates/daemonseed-veilid-net/src/aimd.rs`) SHOULD be reused as the pacer, fed by enqueue-to-ack latency.
- **I6 — keepalive timing independence.** Keepalive dispatch timing must be **statistically independent** of the client's other write load — not merely "small delay": a correlated bias is separable from zero-mean jitter given enough samples. Mechanism is the build's choice (reserved class-4 dispatch capacity is the expected shape). Deliberate cross-record phase-staggering is **forbidden** — a stable phase relationship between a client's records is itself a linkage channel; per-room jitter stays independent, and post-congestion keepalive clustering is absorbed receiver-side (WB-1.10's queue-aware reap suppression + TTL slack), not by dispatch scheduling.
- **I6b — deadline override.** A class-4 write whose target value has a hard DHT expiry (the operator MOTD/announcement keepalive, #158) carries a deadline (TTL − slack); at the deadline it dispatches ahead of class order. Expiry of operator content is data loss, not staleness.
- **I7 — shutdown flush and shed.** On graceful close: pending **chat writes flush** within the close budget alongside leave tombstones and share withdraws (a locally-echoed message silently dropped at close is data loss — the sender saw it as sent); pending class-3/4/5 current-state writes are shed. If the close budget expires mid-flush, remaining writes are abandoned to the TTL backstop — the budget bounds the close, the flush order bounds the damage.
- **I8 — starvation floor.** Every queued write carries a max-age; a write older than its class's age bound escalates one class. Bounds class-5 starvation (a post-warmup advert republish deferred indefinitely would silently re-create the #157 zero-discovery symptom).
- **I9 — no read-triggered writes (WB-0's derived rule, stated as a scheduler invariant).** No read, render, or freshness/reap transition may enqueue a write. The scheduler's enqueue surface is reachable only from user actions, session boundaries, and cadence timers.

The I1 funnel mechanically retires #154's inline-park failure mode (Subscribe/Resweep/Publish parking the actor loop) as a side effect.

## WB-4 — FROZEN: rendezvous discovery rule (settles #157's class)

The panel refuted a placement-only rule: an id-addressed slot IS reachable when readers sweep the whole record blind (announcements are content-addressed today and discover fine), and conversely a perfectly-placed write is invisible if nothing ever re-reads the record after the write lands. Discovery has **two legs**, and a surface must hold both:

- **L1 — spatial leg.** A discovery-class write must land in a record that readers **sweep/watch whole** — the reader never needs to compute the writer's slot from data it doesn't hold. Placement inside such a record (member-region, hash-slot, content-address) is then a collision/geometry concern, not a discovery concern.
- **L2 — temporal leg (the leg #157 actually violated).** A discovery-class write must be **re-surfaced after DHT convergence**: either its readers re-read the record on a steady-state cadence (a slow periodic resweep — reads, riding the WB-2 read lane), or its writers re-write on a cadence that generates fresh ValueChanges for settled watches. A write-once value on a record whose sweeps end at warmup is invisible to any client that converged later — one-shot sweeps + a passive watch do NOT constitute discovery.
- **L3 — declaration.** Any new rendezvous surface declares how it satisfies both legs in its design doc before wiring.

**Per-surface verdict:**

| Surface | Spatial (L1) | Temporal (L2) |
|---|---|---|
| Chat append-ring | ✓ member-region ring, record swept whole | ✓ chat traffic itself generates ValueChanges; backlog via sweep |
| Presence slots | ✓ hash-slot on a whole-swept record (collision: WB-1.11) | ✓ self-healing — keepalives re-write every cadence |
| MOTD / operator | ✓ known constant slot + whole-record sweep; announcements are content-addressed on the same whole-swept record | ⚠ operator keepalive re-writes (#158 expiry is the failure of this leg when the keepalive lapses) |
| Share adverts (post-#153) | ✓ *reachable* — the share record is subscribed, watched, and 0..64-swept | ✗ **VIOLATES L2** — adverts are write-once (re-written only on route churn / watchdog); the joiner's resweeps end at +60s while foreign-content convergence is ~68–112s (#140), so the advert lands after the last sweep and a settled watch gets no fresh ValueChange to deliver. The #157 deadlock is **temporal**. |

**#157 fix direction (frozen: fix the temporal leg; reproduce-before-fix stands):** the cure is a steady-state re-surfacing of discovery records — a slow periodic resweep of the share record (reads: cheap against the write budget, paced in the WB-2 read lane) and/or an advert re-write cadence generating post-convergence ValueChanges (writes: budgeted under WB-2). Re-*placing* adverts to member-region slots changes nothing a 0..64 sweep already covers and would ship a green build that still zero-discovers. The builder MUST first reproduce and confirm the temporal mechanism (the trace signature: both clients sweep the record before the foreign advert converges, and no ValueChange for the foreign subkey arrives afterward) — if reproduction contradicts this diagnosis, the finding returns here before code changes.

**Build note (2026-07-10, #157 landed).** The orinoco felt-test reproduced the temporal mechanism — but on *chat*, not only share adverts: with matching record keys and DHT writes at 36–246s, lobby/circle messages written after the +60s warmup window echoed locally yet never reached an already-settled peer, while share *discovery* itself worked. This refutes the WB-4 table's assumption that chat's own ValueChanges are a *reliable* re-surfacing leg — the passive Veilid watch is lossy, so a whole-record reader resweep is needed for chat too. Per the reproduce-before-fix clause above, the finding is recorded and the fix generalizes the reader-resweep to ALL subscribed chat/discovery records, not only the share-advert record: a post-warmup round-robin `steady_resweep` arm in the gui/tui net actors re-sweeps one record per ~10s tick (key-based cursor so a join/leave never skips a record; WB-2 read lane), presence excluded (self-heals via keepalive re-writes). WB-ISC-14 is built; WB-ISC-15's live two-node oracle is deferred to the follow-up orinoco re-test. Known limitation: per-record latency scales linearly with room count — a high-water tail-sweep is the follow-up lever (see Open questions).

## ISC candidates (register in `ISA.md` + `isc_coverage` at the build commits)

- **WB-ISC-1:** Presence emit timing takes no input from user activity, and keepalive dispatch timing is statistically independent of other-class write load (probe: paused-time test comparing keepalive dispatch-delay distributions under chat-burst vs idle — distributions indistinguishable by KS/correlation test, not merely "within the jitter band").
- **WB-ISC-2:** Anti: presence/roster state for room R never consumes input from any record outside R's own sibling set (probe: unit test with cross-room traffic asserting no refresh).
- **WB-ISC-3:** A connected-but-silent member remains on the roster indefinitely while its keepalives land (probe: paused-time test, silent member, 3× TTL horizon).
- **WB-ISC-4:** A member's roster freshness advances on any verified same-room member write without a presence beacon (probe: unit test, chat-only member stays fresh past TTL).
- **WB-ISC-5:** Reaping is suspended while enqueue-to-ack latency is elevated, and resumes in calm (probe: unit test, elevated signal + expired TTL → no reap; calm → reap).
- **WB-ISC-6:** All presence-class writes (join, keepalive, leave) seal to one constant byte length (probe: unit test asserting equal ciphertext length across all three, all payload shapes).
- **WB-ISC-7:** A leave tombstone dominates freshness: no same-room write with `sent_unix_ms ≤ leave_ms` re-freshens a departed member (probe: unit test, tombstone then late chat → member stays reaped).
- **WB-ISC-8:** Anti: no freshness-inference or reap transition schedules any network emission (probe: code inspection + instrumented test counting emissions across inference/reap transitions = 0).
- **WB-ISC-9:** Steady-state non-chat DHT writes ≤ 4/min per client under the WB-2 load model (probe: the paused-time oracle).
- **WB-ISC-10:** A chat write to an idle record dispatches ≤ 2s after enqueue at any queue depth (probe: paused-time test with a saturated class-4 backlog).
- **WB-ISC-11:** Anti: no chat ring write is ever coalesced or dropped by the scheduler, and pending chat flushes at graceful close (probe: property test — every enqueued chat write reaches `set_dht_value` exactly once, in per-record order, including across a close).
- **WB-ISC-12:** Anti: a queued withdraw/leave is never coalesced away by a same-id current-state write (probe: unit test, withdraw enqueued then watchdog refresh enqueued → withdraw dispatches, refresh dropped).
- **WB-ISC-13:** Slot/seq assignment for ring writes occurs inside the record lock at dispatch (probe: code inspection + the existing interleaving oracle extended over the queue).
- **WB-ISC-14:** Anti: no discovery-class surface relies on warmup-only sweeps plus a passive watch — every discovery record has a declared steady-state re-surfacing mechanism (reader resweep cadence or writer re-write cadence) (probe: per-surface review at each new surface's PR, anchored by the WB-4 table; #157's fix is the first application).
- **WB-ISC-15:** Share adverts are discoverable by a client that holds only the room secret and converged AFTER the advert was written — no prior knowledge of any `share_id`, no reliance on warmup timing (probe: the #157 two-client oracle: B joins/settles first, A publishes after B's warmup window closes, B still discovers).

## Open questions (for the builds, not this freeze)

- Per-record aggregate write load at high membership N (N members × keepalive rate on one record's DHT node set) — hotspot risk; measure at the #77 felt-test before raising room-size ambitions.
- The steady-state discovery-resweep cadence (#157 build): slow enough to respect the WB-2 read lane, fast enough that a fresh share is discoverable in tens of seconds, not minutes.

## WB-5 — AMENDMENT (2026-07-12, DRAFT pending ratification): the write window vs the exogenous DHT floor

> **Freeze scope note.** This amendment freezes the **diagnosis** (AIMD-on-latency is the wrong controller against an exogenous progress-extending fanout regime), the **controller structure** (record-scaled window + acquire-wait guard + shared regime observable with a discovery floor), the **shared-gate budget** (writes + reads share one 16-permit pool; fetch is off it), and the **ratification sequencing** (start `W_max`=2, step up only on the single-client control). Everything else stands unchanged — I1 funnel/classes, I2 per-record single-flight, I3 coalescing/dominance, I4 chat reserved slot, I6/I6b, I7, I8 starvation floor, I9, the WB-1 presence model, the WB-2 ceilings, and WB-4. ### Evidence (2026-07-12 orinoco felt-test + veilid-core 0.5.4 source)

- Raw `set_dht_value` completions (timer wraps only `rendezvous::publish`, downstream of the funnel): dsA **190.8s / 54.5s / 601.3s**, dsB **269.5s / 432.8s / 101.5s**; zero write errors. Offered load at the time: window collapsed to floor=1 — minimal. Three days earlier the same stack measured **1.4–5.8s at ~2/min** (this doc's healthy anchor). The latency regime varies ~100× across days and ~10× within one session, independent of our offered rate.
- veilid-core's set fanout deadline is **progress-extending**: each node accept re-arms the nominal 10s `set_value_timeout_ms` (`fanout_call.rs:642-657`), so a single awaited set legitimately runs minutes on a churny network while making progress. The observed floor is real fanout behavior, not a defect on either side.
- **All DHT network ops share one process-global 16-permit semaphore** (`storage_manager/mod.rs:177,224`, `network.dht.max_concurrent_operations`, default 16 — a normal config knob, not footgun-gated). Sets on distinct records scale ~linearly up to that gate; **reads take the same gate**, so the WB-2 read lane and this write lane draw on one shared pool. (Our sweeps issue GETs strictly sequentially with an in-flight guard, so today reads hold ~1 permit.)
- `Ok(None)` from `set_dht_value` does **not** certify consensus durability: it is returned on full consensus, on ≥3-node partial consensus at timeout/exhaustion, and on failure-with-`allow_offline` where the write was only queued for veilid's background offline flush (1s-tick re-fanout). Our `write ok` trace line means "dispatched and accepted," not "network-durable." `allow_offline` defaults to true, so the background flush safety net is already active.

### Diagnosis

AIMD's multiplicative decrease assumes high latency = congestion the sender caused. Here (a) offered rate is already priced upstream — WB-1 cadences + I3 coalescing + the WB-2 ceiling bound steady demand at ~2–2.5 writes/min, below the measured-healthy anchor — and (b) breach latency is dominated by the exogenous fanout regime. Running AIMD against that signal collapses the window to 1 and strips cross-record concurrency (the only throughput lever, hard-capped at the shared 16-permit gate) exactly when per-write capacity is scarcest: non-chat convergence degrades to O(records × regime-RTT), the "no presence / no discovery for minutes" symptom. The fork verdict: **Option A's discrimination and Option B's record-scaled concurrency are both right and compose; Option C's measurement rider is adopted alongside** — the controller was wrong AND the floor is real.

### The shared gate (established this session — the budget everything below is denominated in)

- **DHT reads and writes share ONE 16-permit process-global semaphore** (`StorageManager::operation_concurrency`, `storage_manager/mod.rs:177,224`; `get_value.rs:105` and `set_value.rs:127` both `acquire_operation_gate`). A permit is held for the set's **full** duration — up to the measured 601s tail. So the write lane and the WB-2 read lane (sweeps/resweeps are GETs) draw on **one shared pool**; their combined in-flight is the budgeted quantity.
- **Content fetch (`app_call` over private routes) is OFF this gate** (`rpc_app_call.rs:9-35` reaches `rpc_processor`, never `StorageManager`; no shared semaphore). So the fetch window (#109/#113) does NOT contend the DHT budget — the F1 "6 writes + 8 fetch ≫ 16" catastrophe does not arise. The budget is `W_max (writes) + read-lane in-flight ≤ 16 − margin`; fetch is independent.

### I5′ — the amended invariant (replaces I5's controller; the rate bound remains)

1. **Record-scaled window, gate-denominated, measurement-gated numeric.** Non-chat in-flight target = `min(distinct records with pending writes, W_max)`. **`W_max` starts at the frozen value 2** and steps up ONLY after the §I5′.5 single-client control run confirms the regime is offered-rate-independent for that network (advisor + F3: shipping the 3× jump to 6 on an unverified premise is the sequencing error). `W_max` is a **hard permit ceiling** reconciled with the shared gate: `W_max + read_lane_reserve + chat_reserve(1) ≤ 16 − margin`. The band **ceiling is derived from that arithmetic, not chosen round** (the earlier [2,12] is withdrawn — 12 write permits alone is 12/16 before any read draw); with sequential sweeps holding ~1–2 permits the safe post-measurement ceiling is ~4–5, and it is an **enforced app-level accountant** (a daemonseed-side limiter above veilid's gate whose write+read total is provably ≤ 16 − margin), not a declarative number. **Chat (I4) and the I8 starvation floor are reserved against the SEMAPHORE, not merely the window** — they acquire a permit ahead of any class-3/4/5 write when the pool is near-saturated, so a backlog of minute-long writes can never make chat block on *permit acquisition* (F1's failure mode a window-only reserve misses). Per-record single-flight (I2) is untouched — the window only widens ACROSS records.
2. **Self-congestion guard signals on permit-acquire-wait, biased to HOLD (F2/F4).** The 07-12 exogenous regime and self-induced gate-saturation are **not** separable by a per-in-flight-bucket latency slope — shared-gate contention presents as a *uniform* offset across the write lane's own in-flight levels, so a bucket-slope test is blind to it (F2, the deepest finding). The discriminator is instead **permit-acquire-wait** — the delay between scheduler-dispatch and the set actually entering fanout, measured distinct from fanout latency: elevated acquire-wait ⇒ decrease (real contention); high fanout latency with low acquire-wait ⇒ HOLD (exogenous floor). If veilid cannot surface acquire-wait through the sink, the guard falls back to the §I5′.1 hard accountant as the sole safety element and does not attempt slope discrimination at all. Decrease is **asymmetrically gated** (F4): it requires a minimum per-bucket sample count and sustained (not single-sample) evidence before halving, because a false-hold is bounded by the static `W_max` + the untouched rate ceilings (cheap) while a false-decrease reintroduces the O(records × RTT) pathology this amendment exists to remove (expensive). The margin `k` is calibrated from the §I5′.5 control data, not guessed. Enqueue-to-ack remains an input; the fixed 10s threshold is retired (it mapped to veilid's nominal timeout, which the fanout legitimately exceeds while progressing).
3. **One DHT-weather observable, with a discovery floor on its consumers (F5).** The transport publishes a per-session regime estimator (EMA of DHT op latencies). Consumers: WB-1.10 reap-in-calm, the #172 stop-on-quiet resweep backoff, and the UI honesty state. It is an observable, not a controller — no consumer may enqueue writes from it (I9 stands). **The #172 backoff carries a WB-4.L2-derived floor cadence: elevation may SLOW the discovery resweep but must never STOP it** — otherwise, during the exact bad regime WB-5 targets, writes are slow AND the resweep backs off → #157 zero-discovery walks back in for the regime's duration (F5). EMA smoothing + hysteresis bound the (balancing, non-divergent) backoff hunt.
4. **Presence honesty under reap-in-calm (crypto/privacy MED).** When reaping is suspended (elevated regime, WB-1.10), the roster surfaces a "presence may be stale" signal. Roster-as-presence is a trust input for sharing decisions; a suspended reaper shows departed members as present, so the suspension must be visible, not silent.
5. **Measurement rider is a ratification gate, not a follow-up (F3/F6 + Option C).** Before `W_max` steps above 2: an attended single-client control run (same records, one client, existing `DAEMONSEED_VEILID_TRACE=1` recipe) records write latencies vs the two-client run. Single-client ≈ two-client ⇒ regime confirmed offered-rate-independent for that day's network ⇒ authorize the step-up and calibrate `k`. The same run records the `Ok(None)`-with-offline-queue rate at the candidate window vs 2 (F6: higher concurrency in a bad regime queues more veilid background re-fanout — write amplification one layer down, invisible to WB-2's own-enqueue accounting; measure it for near-zero cost). Registered WB-ISC-19, `[DEFERRED-VERIFY]`.

### Withdraw durability (crypto/privacy MED — stated honestly)

`Ok(None)` from `set_dht_value` does not certify durability (§evidence): with `allow_offline` (default true) a returned withdraw may only be *queued* for background flush, so "unpublish returned OK" can leave a sensitive share still discoverable until the flush lands. **The catalog TTL backstop is the real confidentiality guarantee for a withdraw — no code treats a returned withdraw as "it's gone now."** (Veilid behavior, not introduced here; surfaced because WB-5 is where the durability semantics were established.)

### Write-storm guard (the preserved WB-3 guarantee — restated honestly per advisor + F1)

The 2026-07-09 saturation was an offered-**rate** phenomenon (~6+/min); this amendment changes in-flight **concurrency**, and every rate bound stands (WB-1 cadences, I3 coalescing, the ≤4/min WB-2 ceiling, I9). But the storm's *symptom* (chat starved, minute-long writes) has a second reachable cause the naive amendment introduces: raising the write lane's shared-gate footprint from 2 to N permits, each held for minutes, squeezes the read lane that fixes #157 and refreshes presence (F1). The claim "same cause won't recur" is true but insufficient; the symptom is foreclosed instead by **(i) the enforced cross-lane accountant keeping write+read in-flight provably under the 16-permit gate, (ii) starting at `W_max`=2 and stepping up only on measured evidence, and (iii) chat + floor reserved against the semaphore.** Genuine self-induced contention still decreases the window via the acquire-wait guard. This is the shown version of the guarantee, not the asserted one.

### What the write lane cannot fix (stated honestly)

- Per-record chat delivery = one set-RTT (ring-seq inside `record_lock`, I13/#131 — not reopened). In a 200s regime, a chat message lands in ~200s no matter how the window is set. The mitigations live elsewhere: local echo (exists), the weather-driven UI honesty state (above), and veilid-level levers.
- The regime itself. Bootstrap/route health and fanout tuning are veilid's domain; the footgun-config DHT knobs remain out of scope for a stock build.
