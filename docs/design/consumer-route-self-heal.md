## Problem

Felt-test (v0.33.1, Linux + Windows consumers, 2026-07-15): every consumer failed to list a discovered share. Restarting the **consumer** fixed it; restarting the **server** did not, and the manage-shares Refresh fixed neither. The grounded trace (all sites re-verified 2026-07-15; citation audit passed):

- The consumer caches the sharer's private-route blob per share (`shares.discovered`, gui `veilid_net.rs:327`; tui equivalent) and re-imports that cached blob on every browse (gui `veilid_net.rs:2092-2110`) — the blob is refreshed only when a fresh verified `ShareAnnouncement` arrives.
- Fresh announcements arrive via a DHT watch registered once per session (`actor.rs:1447-1449`) plus the WB-4 steady resweep (15s tick, `STEADY_RESWEEP_TICK`, gui `veilid_net.rs:169`). The record-open cache has deliberately no error-path invalidation (`rendezvous.rs:134-140`).
- **The sweep swallows GET errors** — the get closure in `sweep` is `.ok().flatten()` (`rendezvous.rs:287-291`), so an erroring record session produces silent zero-yield sweeps forever. The 15s resweep cannot heal what it cannot see. This is the primary observability gap; the never-invalidated open cache is only unfixable *because* nothing can observe that it is dead.
- The server already self-heals its published route (advert watchdog, `actor.rs:1516-1532`, 150s cadence) — which is why restarting the server changes nothing a broken consumer can see: the fresh advert lands in the record, and the consumer's dead session never delivers it.
- #180 item 2: `release_private_route` returned `Invalid argument` on a valid-looking `VLD0:` key during advert republish (`actor.rs:1575` — already trace-level there), and consumer-side `import_route` calls (gui `veilid_net.rs:2101,2249`; tui `veilid_net.rs:1124,1180`) have no matching release.
- #180 item 3: during ~60s of failing fetch retries, chat was starved. Mechanism (grounded): the GUI net actor (`veilid_net_actor`, gui `veilid_net.rs:395`) processes all `NetCommand`s serially through `handle_command`, and `NetCommand::FetchShare` is awaited **inline** (gui `veilid_net.rs:1026`) — a slow failing fetch parks the same loop that processes `SendCircle`/`SendLobby`. This is #154's inline-park class at the GUI layer; the WB-5.1 pools cannot help because the starvation happens above them.

## Evidence — three premises corrected against veilid-core 0.5.4 source (2026-07-15, panel-audited)

These corrections shrink the design; they are stated so the build does not re-add machinery the transport already provides.

1. **Watches self-renew in veilid 0.5.4.** The `OutboundWatchManager` holds per-record *desired state* and reconciles continuously — `needs_reconcile` fires on empty state, dead nodes, low consensus, expired per-node watches, changed params, and a fallback inspection catches missed changes (`outbound_watch_manager/outbound_watch.rs:185-256`); renewal runs pre-expiry on `RENEW_OUTBOUND_WATCHES_DURATION` = 30s (`constants.rs:20`), driven by a periodic tick task, and desired state is persisted to `metadata_db` across restarts. "Registered once, silently cancelled, must be re-watched" is pre-0.5.x doctrine. App-level periodic re-watch is **not needed**; a re-watch is needed only after a record re-open (watch state is per-open; `close_dht_record` sets the desired watch to cancelled, `close_record.rs:117-119`). The watch's *lossiness* (missed ValueChanges) is real and already priced by the WB-4 steady resweep.
2. **The consumer import leak is bounded, not unbounded.** Remote route import dedups — "it is safe to add the same route more than once and it will return the same route id" (`route_spec_store/route_remote.rs:56`, on `import_single_remote_route`; `import_remote_route_blob` shares the content-derived-id `add_remote_route` mechanism) — and the remote-route cache is an LRU with expiry (`route_spec_store_cache.rs:319-381`). Re-importing the same cached blob every browse costs one cache entry per *distinct* blob, not per browse. The release pairing in §RS-3 is hygiene, not an emergency.
3. **The `release_private_route` "Invalid argument" is benign-by-spec.** Veilid returns `InvalidArgument` for a route id that is "unknown, already released, or malformed" (`veilid_api/api.rs:509-511`), and veilid itself evicts dead routes (`take_dead_routes`). Releasing a route the transport already GC'd is an expected race, not corruption. The fix is tolerance (§RS-3), not key surgery.

One thing deliberately **not** claimed: the exact veilid-level mechanism that killed the consumer's record session in the felt-test (GET-error streak vs. reads pinned to a stale local copy vs. a dead sweep task) is unconfirmed — and Evidence 1's watch persistence makes it *more* puzzling, not less. §RS-1.3's detection ladder and the repro-first gate carry that honestly.

## RS-0 — The emission-class ruling (Q1: the WB-0 crux)

**Question:** is a share-listing/manifest re-fetch — and the route re-resolve GET behind it — content-class (WB-0-exempt) or discovery-class (WB-0-governed)?

**Ruling: the fetch and the re-resolve are different emissions on different observer surfaces, and they classify differently.** Three emission classes plus one provenance rule, each clause anchored to frozen text:

- **Content surface — consented.** The manifest/chunk fetch is an `app_call` over the sharer's private route. WB-0's exemption clause names content fetch verbatim: "content fetch is the user's explicit consented emission." Its observer class (route relays, the sharer) sees the user's deliberate transfer act — that is the product. **Bounded retries of a consented fetch are the same surface and the same observers**; the one residual a retry adds beyond a fresh fetch — a timing signature that could mark it *as* a retry — is closed by the decorrelation rule in §RS-1.4 and named in §Residuals.
- **Discovery surface — cadence-only, consent does not transfer.** Any DHT GET, open, or watch on a lobby/share record is a presence/discovery-class emission ("write or read-fetch" — WB-0 verbatim). The frozen exemption names chat and content fetch *only*; a browse-click does not extend it to the discovery surface, because consent is per-observer-surface: the lobby record's storage host would learn "this client's user is active right now" from a browse-timed re-resolve GET — exactly the residual (session rhythm, reading activity) WB-0 exists to protect, and exactly the frozen forbidden example ("an on-demand GET triggered by opening a room or checking a roster"). **A browse-triggered re-resolve GET is therefore forbidden**, even though the browse itself is deliberate.
- **Errors do not launder provenance.** An error's provenance chains to the act that triggered the parent operation: a fetch failure is browse-timed, so an error-triggered discovery emission is an activity-timed emission wearing an error costume — the derived rule ("no read/render event may enqueue a non-cadence emission") applies transitively. Per WB-0's first sentence, an error may influence **local computation only**: stale marks, parked retries, repair flags, UI state.
- **Session boundaries.** Startup and the connect window are frozen allowances. Manual Refresh is **not** granted a general re-establishment exemption (the panel refuted the draft's ISC-S30 reading: that hook prices a refresh-moment *roll-call write*, not a multi-record open/watch/sweep burst; and a re-establishment fingerprint on a *healthy* record would be a clean "user pressed Refresh at T" signal to a storage host). §RS-4's contract is instead built to be traffic-shaped like cadence for healthy records, with re-establishment conditioned on network-failure evidence.
- **The repair-provenance rule (the keystone).** A repair emission (re-open, re-watch, repair sweep) is legal iff (a) its *evidence* was gathered exclusively from network-state observations — sweep error counts, watch state, the weather estimator — and (b) its *dispatch* rides a cadence tick. Under (a)+(b) the repair signal is a function of **network state only**: no user-derived bit ever enters its input chain, so its emissions cannot encode user activity — informationally sterile by construction, not by policy. The observer that sees a repair re-open is the same host that served (or failed to serve) the GETs constituting its evidence; it learns nothing about the user. *(Dispatch-ordering note, panel: a join/leave reshapes the cursor's key-ordered set and can shift a pending repair's dispatch slot by ≤1 tick — non-informative, because joins/leaves are themselves already-emitted session-boundary acts and the shift discloses no additional activity.)*

**Why this is hard-to-vary:** exempt the re-resolve GET under browse-consent and the lobby host gets an activity oracle (drops the second clause); let errors launder and every forbidden emission returns via a contrived failure (drops the third); grant Refresh a blanket re-establishment exemption and healthy-record re-opens fingerprint the user's hand (drops the fourth); let repair take evidence from fetch errors and repair timing becomes browse timing one hop removed (drops the keystone). Each clause closes a distinct leak; none is decorative.

**Consequence:** the self-heal's reactive path performs **zero network actions**. Everything that touches the network is either already-running cadence (the steady resweep, now able to see), a cadence-dispatched repair (evidence-sterile), or a consented content-class act whose retry timing is deliberately decorrelated (§RS-1.4).

## RS-1 — The mechanism (Q2: reactive vs proactive, resolved as "cadence-repair + local-only reactive")

The fork the brief posed — on-error re-resolve vs. proactive route TTL vs. periodic watch renewal — dissolves under the corrected evidence: periodic watch renewal is redundant (veilid self-reconciles; Evidence 1); a consumer-side proactive "route TTL" cannot re-derive anything (only a fresh advert can — the sharer's watchdog already provides rotation at 150s); and on-error re-resolve is WB-0-illegal (§RS-0). What remains:

1. **Sweep error accounting (the enabling fix).** The get closure `sweep` passes to `sweep_gated` drops errors (`.ok().flatten()`); both the closure and `sweep_gated`'s return type change so per-record `(gets_attempted, gets_failed, slots_found)` reaches a per-record session-health tracker in each frontend's net actor. Pure observability — no emission change — but it edits the shared #157 resweep core, so the build regression-guards existing resweep behavior (the #157 contract itself is untouched).
2. **The cadence repair arm.** A record whose last **K consecutive** sweep passes all-failed (or whose watch is reported dead, where veilid surfaces it), **while the weather estimator reads calm**, is repaired **at the K-th failed pass's own cursor tick** — evidence-complete and still cadence-timed, avoiding a wasted extra cursor round. Repair = re-establish the record session: invalidate the `open_cached` entry, re-open, re-watch, full 0..64 sweep — **holding the record's `record_lock` across the entire re-establishment**, so a concurrent same-record write can never target a torn-down handle (the lobby record's open key is shared by the lobby subscription, every share advert, and lobby chat writes — the exact hazard the open-cache's no-invalidation comment warns about; the lock is what makes deliberate eviction safe where ad-hoc eviction was not). Whether re-establishment needs `close_dht_record` first or open-in-place suffices (veilid updates an already-open record in place, `open_record.rs:155-170`; close cancels the desired watch, `close_record.rs:117-119`) is repro-gated — see Open questions. All GETs per-GET through the read pool; open/watch acquire the §RS-2 margin limiter. One repair in flight at a time (the existing `resweep_busy` guard serializes ticks).
   - *Weather gating:* elevated regime suppresses repair (GET timeouts in a bad regime are weather, not death) — same signal, same reasoning as reap-in-calm. Suppression delays repair; it never cancels it.
   - *Decaying backoff on repeated failure (advisor):* a record whose repair does not restore service (sweeps still failing) doubles its K-threshold per consecutive failed repair, capped (initial cap 8×) — a permanently-dead record (abandoned circle, sharer gone forever) settles to one bounded re-establishment attempt per ~52 min instead of every K rounds indefinitely. Backoff resets on the first successful pass.
   - *The healing envelope (panel-corrected arithmetic).* Detection worst case = K full cursor rounds = K × records × tick — at the current census (~13 records, 15s tick), K=2 ≈ **6.5 min**; repair itself (open ~6-10s + re-watch + 64 GETs) adds ~30-60s. Single-dead-record heal ≈ **≤ ~7.5 min** in calm weather. The **all-records-dead** case (post-blip) serializes repairs behind `resweep_busy` at repair-*duration*, not tick cadence: ≈ detection + records × repair-duration ≈ **13-20 min** — stated honestly; the lever is K and the tick, both build-tunable against the reproduction, and detection matters precisely when ticks stretch.
3. **The detection ladder (honest about the unconfirmed death mode).** L1: GET-error streak (visible after step 1). L2: watch-death state where veilid surfaces it. L3: **if** the reproduction shows a stale-local-read mode (GETs "succeed" against a pinned local copy), a cadence-timed freshness probe (e.g. seq comparison via inspect) — *designed only if the repro demands it*. **Repro-first gate:** the build reproduces the dead-consumer state (two-client, kill/rotate the sharer route with the consumer's watch+session aged) and confirms which rung fires *before* finalizing detection constants; if the reproduction contradicts L1/L2, the finding returns here before code changes.
4. **The reactive path — local-only, decorrelated retry.** On manifest/chunk fetch failure (after the existing bounded fragment retries): mark the share's route `Unresolved` (stale), park a **one-shot, generation-tagged** deferred retry keyed to `(share_id, discovered-generation)`, surface honest UI state ("re-resolving — the share stays listed"). When a fresh advert for that share folds, the retry does **not** fire at the fold event — it fires at the consumer's **next steady-resweep cursor tick** (same discipline as repair dispatch), so its timing rides the consumer's own cadence rather than the sharer's re-announce cadence; without this, retries cluster within one RTT of the sharer's watchdog re-announce and become distinguishable from fresh fetches — a "this consumer's earlier browse failed" bit to the sharer (§Residuals). Window-bounded: the window must cover detection + repair + fold + one tick — **10 min** initial (≈ 390s detection + 60s repair + one tick + margin); on expiry, surface failure and clear the parked retry. A generation mismatch (share withdrawn/re-added while parked) drops the retry. The share is **never pruned by this path**.
5. **Fetch-path pruning is retired entirely — both gui sites.** Systems analysis confirmed prune-on-fetch-fail as a Fixes-That-Fail loop (transport failures deleting live shares destroys the repair loop's own work-list); the panel then refuted the draft's plan to keep the *import-failure* prune arm: an `import_route` failure is transport/route-death, **not** a malformed blob — the blob's binding and route signature were already verified at discovery (`apply_discovery`'s `share_binding_is_valid` + `verify_route_advert` gates), and non-decodable envelopes never enter `discovered` at all. So both gui fetch-path prune sites (import-fail `veilid_net.rs:2106`, manifest-fail `:2126`; the tui prunes only on fetch-fail) convert to the same `Unresolved` event path. This is also what makes §RS-2's off-loop spawn possible: `prune_unreachable_share` was the fetch path's only `&mut ShareState` use. Prune keys on authoritative signals only — verified withdraw (owner-bound) and catalog receive-time TTL.

## RS-2 — Gate placement, the margin limiter, and chat safety (Q3)

> **Amendment 2026-07-17 (reframe, ratified) — the auto-re-download is retired.** An attended DIAG-instrumented two-client felt-test refuted this design's premise of a consumer-side death mode: the route-refresh path already works and is prompt (a returning sharer's fresh route re-imports in ~54s via the veilid **watch push**, which survives a sharer hard-kill; the residual latency is the sharer's veilid warmup, not a consumer bug). So the self-heal's job is **route freshness, not download completion** (a sharer may be gone minutes → days → forever). **The mark-fetchable-again is now owned by the route-rotation fold** (`apply_discovery` clears the share's `Unresolved` flag exactly when the route blob rotates — a purely-local no-network op): keyed on the route rotating rather than on the parked-retry window, so a share recovers *however long* the sharer is away (the 600s window no longer bounds recovery), and gated on an actual rotation not a mere generation bump, so a content-only re-advert (route unchanged) never flips a share to fetchable-looking against a dead route. Because clearing emits nothing to the network, it is legal at the fold (CRSH-ISC-15's decorrelation binds *network* dispatch, not a local UI-state flag). The parked browse retry becomes **housekeeping only**: it no longer re-fetches or clears `Unresolved` — a Fire tick drops a now-stale park (generation bumped without rotation), expiry surfaces a give-up hint (naming the share), and a withdraw drops it. This SUPERSEDES the "parked fetch retry → `app_call` content fetch" clause in the third bullet below and reduces the "retry-existence bit" residual (§Residuals) to nil (the retry issues no manifest request). §RS-0 Q1 resolved with no emission-class change (removing an op is trivially safe); de85cca's route-rotation re-import (CRSH-ISC-27) stays, as a necessary sub-case — the rotation both re-imports the route and marks the share fetchable. A follow-up may retire the now-vestigial parked-retry subsystem entirely (reworking CRSH-ISC-6/15/19/23); this amendment keeps it as bounded housekeeping. The bullets below are retained as the design-of-record; read them under this amendment.

- **The un-gated-op margin limiter (new, load-bearing).** §I5″.1's margin invariant was a census argument ("open/watch are issued inline in the serial actor command loop, ≤1 in flight"); this design adds un-gated call sites in *spawned* contexts (the repair arm rides the spawned resweep task; Refresh processes multiple records), which the frozen clause explicitly makes this design's obligation. Discharge by construction: a capacity-`margin(2)` semaphore (the un-gated-op limiter) that **every** `open_dht_record`/`watch_dht_values` call site acquires — the existing subscribe path, repair, and Refresh alike. Peak un-gated concurrency ≤ margin(2) becomes enforced, not asserted, under any composition of concurrent connect + repair + Refresh (CRSH-ISC-14's live probe). Repair and Refresh must never hold a read-pool permit while acquiring the limiter (WB-ISC-28's single-permit rule extends to it).
- **Every new network op is classified:** repair/Refresh GETs → read pool, per-GET (WB-5.1 §I5″.2); repair/Refresh open/watch → un-gated, limiter-bounded; the parked fetch retry → `app_call`, off-gate entirely (WB-5 evidence: content fetch never touches the DHT semaphore); **zero new DHT writes** — the design's steady-state write cost is exactly 0/min, leaving WB-2 arithmetic untouched (panel: I9/WB-2 conformance survived attack).
- **The I4 chat bound is protected at the layer it was actually breached.** The WB-5.1 pools already isolate chat at the DHT gate; #180 item 3 breached it one layer up, in the GUI net actor. Fix shape: `NetCommand::FetchShare` copies the route blob + room key out of share state and **spawns** the fetch; the actor loop returns to its select immediately. Fetch outcomes — success, failure/stale-mark, and the imported RouteId — return as **generation-tagged events** folded on-loop (a stale-generation event no-ops). Enabled by RS-1.5 (the fetch path is now `&mut`-free). The same restructure applies to the TUI actor.
- **Retry discipline:** fragment-level retries stay as built (3 × 250ms backoff — bounded, content-class); the share-level parked retry is one-shot per browse request. No retry loop at any layer is unbounded, and no retry re-enters the DHT gate.

## RS-3 — Route lifecycle (Q4: scope ruling)

**In scope here (the self-heal touches these exact sites):**

- **Consumer release pairing with an in-use guard.** The net actor keeps an **on-loop** map of each discovered share's last-imported `RouteId`, fed by the spawned fetch's import event (the on-loop map is authoritative; a spawned fetch never releases anything itself). Release fires on the **later of** advert-blob replacement or completion of any in-flight fetch/download using that RouteId — a consumer-side analog of the sharer's `SERVE_RECENCY_WINDOW` protection, closing the race where an advert `Updated` mid-download would release the route the download is streaming over. Releasing after each fetch is pointless churn — the next browse re-imports to the same id (Evidence 2); replacement-time release is the hygiene point that frees dead entries early, and the LRU/expiry remains the backstop.
- **`InvalidArgument` tolerance, made structural.** The actor's four release sites already trace rather than fail; the design's addition is a single `release_tolerant()` helper through which **all** release sites route (actor `1031/1575/1635/1668` + the new consumer sites), treating `InvalidArgument` as already-evicted (Evidence 3) — probed by "zero raw `release_private_route` calls outside the helper." The felt-test's "release rejects a valid key" dissolves: the key was valid; the route was already gone.
- **Sharer-side map hygiene:** on `RouteChange::dead_routes`, drop matching `advert_routes` entries so the next republish doesn't attempt to release an already-evicted id (removes the error's most common source rather than merely silencing it).

**Out of scope → #163/#175:** the general route-release audit (every allocation site paired, shutdown release order, withdraw-path route teardown) and any change to route *allocation* policy. This design's rule for its own additions: every route this mechanism imports is release-paired as above; it compounds no leak.

## RS-4 — The Refresh contract (Q5, panel-reshaped)

Manual Refresh is the user-consented accelerant — but it must not fingerprint itself to storage hosts (§RS-0), so it is **sweep-first, re-establish-on-evidence**:

1. **Sweep pass:** immediately full-sweep every share-bearing subscribed record through the read pool — traffic-shaped identically to the steady resweep (GETs on existing sessions; no open, no watch), i.e. to a storage host a Refresh over a healthy record is indistinguishable from a coincident cadence resweep. Results feed the same session-health tracker as cadence sweeps.
2. **Evidence-gated re-establishment:** any record that is already repair-due, **or whose Refresh sweep pass just failed** (weather calm), is re-established immediately within the Refresh — invalidate + re-open + re-watch + re-sweep, under `record_lock`, through the margin limiter, serialized in limiter-bounded waves. The evidence is network-served failure (the keystone argument applies: the host that would observe the re-open is the one that failed to serve the GETs); a healthy record is **never** re-opened or re-watched by Refresh (anti-criterion CRSH-ISC-16).
3. **Retry wake:** parked retries whose shares' adverts have folded fire on the next cursor tick as usual; Refresh does not bypass the decorrelation rule.
4. **Re-render** from the re-folded catalog.

This keeps the one-click heal: a genuinely dead session fails its Refresh sweep on the spot and is re-established in the same action — without waiting out K cadence passes — while a healthy session shows nothing but reads. No writes (the sharer-side re-announce half of Refresh is the 33.2 reindex sibling, already locked — this design adds no consumer-side write). Refresh remains rate-safe: a read burst bounded by the read pool + re-establishments bounded by the limiter.

## Residuals (named, accepted — honesty over marketing)

- **The retry-existence bit.** A parked retry that eventually fires tells the *sharer* (an in-room peer who already receives fetch receipts) that this consumer's earlier browse failed — the decorrelation rule removes the *timing* signature (retries are not distinguishable by clustering at re-announce), but the sharer could still infer retry-ness from a repeated manifest request without an intervening download. Bounded: in-room-peer surface only (the WB-0 trust boundary already excludes in-room peers from presence privacy), protected observer classes see nothing (private routing strips source; the app_call is off-DHT).
- **Refresh-on-dead-record visibility.** A Refresh that re-establishes a dead record emits an open/watch at user-action time toward whatever hosts serve the re-opened record. The evidence-conditioning bounds this to records that just failed network service — the same sterility argument as repair — but the *conjunction* (user pressed Refresh AND the record was dead) is weakly user-timed. Accepted: the alternative (wait out K cadence passes) sacrifices the product's one manual recovery affordance; the emission is rare, failure-conditioned, and invisible on healthy sessions.
- **Repair-visibility to the failing host.** The host that served K failed passes sees a re-open. It learns its own failure was noticed — nothing about the user. Shared by every candidate repair design.

## ISC candidates (register in `ISA.md` + `isc_coverage` at the build commits)
